# 按用户测试手册开展六任务测试

本流程依据你提供的《OptiFlow用户测试手册.docx》实现，协议标识为 `production_manual_v1`，问卷版本为 `manual_survey_v1`。手册原文件未修改。手册中的任务说明、参与者自述与结束访谈在网页收集；观察者完成情况、实测耗时与复盘由组织者在后台填写。

## 组织者准备

1. 打开当前外网管理地址并登录。
2. 在“参与者邀请”选择“工厂生产计划”，创建尚未使用的新邀请，下载链接 CSV，再将各自链接发给参与者。
3. 每位参与者用自己的链接开始；无需下载 Word、安装 Python 或单独发送问卷文件。

已开始的旧测试保留原版协议与简短问卷，不把历史操作改写成新六任务记录。要验收新流程，请用一个未开始的新生产案例邀请。其他两类案例继续原版体验。

## 参与者路径

进入邀请后填写优化背景，点击“开始六任务体验”。此时只记录开始时间，不代替参与者创建任务。页面进入工作台总览，可使用实际新建、模型、结果页面；顶部显示当前任务，侧栏可随时打开“测试任务指引”。

| 任务 | 工作台中的操作与回答 |
| --- | --- |
| T1 开始制定生产计划 | 从工作台找到新建入口，阅读固定工厂需求并生成模型，再记录本步。 |
| T2 看看系统理解得对不对 | 阅读模型，用自己的话说明目标和业务要求。 |
| T3 检查有没有遗漏 | 记录遗漏、误解或不合理之处；没有发现也可如实说明。 |
| T4 增加一条新要求 | 先确认并求解初始模型，保留 v1；再自行输入“A 产品每天最多只能生产 100 件。”并重新建模。 |
| T5 看看系统给出的建议 | 确认修改后的模型并求解，查看结果，记录产量、利润和仍需核实的事项。 |
| T6 比较两次生产计划 | 打开“前后方案对比”，查看 v1 和当前版本，记录差异及向老板解释的方式。 |

每个操作页上方显示本步目的、通俗解释、操作顺序和六步进度；在同一页下方的“本步记录”填写回答、网页使用问题和是否得到他人提示。顶部链接可直接定位到记录表，不需要来回切换测试指引。

点击“提交本步记录，进入下一步”后，回答和问题写入后台，并自动打开下一步对应的工作页面。T2、T3、T5、T6 需要文字回答，系统不会依据内容自动判定理解正确。完成 T6 后进入“结束问卷”。网页中的指引不算他人提示，这一项只记录是否有人帮助参与者。

即使操作卡住，也能点击“先保存问题，不结束本步”。草稿写入数据库，重新访问自己的邀请后可继续填写；保存问题不会虚报步骤完成。T1 尚未创建任务的草稿也会在后台“六任务开始记录”中显示并可导出。侧栏“测试任务指引”保留完整手册和自己的已保存记录。

若确实无法继续，可保存问题后结束为未完成，照常填写问卷；中断记录不算操作完成。此版加入明确的网页操作引导，分析时应注明体验版本，不宜直接与无指引旧版混算独立完成效果。

**初始方案必须先求解。** 手册要求比较两份生产计划，不能只保存一份未求解模型。因此在 T4 前补充初始求解步骤；后台会阻止尚无初始方案时直接覆盖它，求解仍须用户亲自确认模型。

**新要求不一定改变结果。** 当前固定工厂案例中，初始最优方案已经是 A 100 件、B 200 件、利润 10000 元；追加 A ≤ 100 后仍是同一方案。页面如实显示零变化，这也可以作为解释任务。没有把上限改成 80 来人为制造差异；如以后要测试明显变化，应明确修改整套测试协议，避免不同参与者用不同题目而混算。

模型页默认展示“业务与模型对照”：每一行把原文与系统转成的规则并排显示。重新建模后显示上一版与当前版本编号，优先展示新增、修改和移除项，原有项标为“保持不变”。最初的业务需求与后续补充分别显示；数学表达和完整模型按需展开。T1 是提交业务需求，T2 是检查系统对同一需求的理解；到 T4 补充要求后才生成新版本。

补充需求支持“A 每天最多生产 100 件的新要求”等常见单条数量限制说法，也可切换“选择产品和数量”，直接指定决策项、上限 / 下限 / 固定数量。混合多条要求或无法明确识别时不会忽略其中部分，输入会保留并提示调整。

结果页与最终对比页均提供“本次生产决策建议”，直接展示建议产量、利润、执行建议及变更影响。建议只在当前版本已确认、求解最优且数值检查通过时生成。相同结果会说明可沿用原方案；不能把“新增规则”误解为“产量一定变化”。问卷页也提供返回决策建议的入口。

## 内置结束问卷

- 理解度：完全能理解、基本能理解、不太能理解、完全无法理解。
- 最困难环节：理解业务规则、判断是否遗漏约束、补充修改需求、理解决策结果、其他；选择其他时填写说明。
- 刚才哪个地方最让你困惑？为什么？
- 你是否愿意在真实工作中使用？需要哪些条件？
- 如果只能改进一处，你希望改哪里？

三道访谈题保存参与者原话，可如实写“没有”或“不确定”。操作完成和问卷提交分别记录；没有提交问卷不会被显示为已提交。提交成功会明确提示组织者已可查看和导出；参与者可修正后再次提交，数据库事件保留历次提交。

## 后台收集与观察

进入“全量数据与导出”，选择“查看参与者回答与问卷”，即可查看六步回答和完整访谈。展开“查看手册回答与填写观察记录”，组织者可为每步记录独立、提示、未完成或未测试，填写实测耗时、发现问题，以及关键技术异常、最严重问题、影响和可能原因。

“导出可用性测试 CSV”包含专用任务、各步回答、网页问题自报与说明、草稿保存时间、提示自报、模型版本、问卷字段和观察记录。另有“六任务开始记录”及 CSV，包含开始 T1 后尚未创建任务的人及其问题草稿，便于跟进新建入口的流失；下方完成率明确只统计已创建专用任务的记录，不把这部分遗漏解释成已完成。

系统记录的每步经过时间从该步开放计至参与者提交，包含求解等待和离开页面，**不能视为实测操作时间**。观察者未填写时保留空值或“未测试”，不能把点击继续解释成独立完成。预设错误验证继续使用测试开始前固定的核查标准和后台人工评定，不向案例暗中植入错误。

## 存储与兼容

继续使用同一 `runtime/tasks.sqlite3`。新增 `study_manual_sessions` 保存协议、背景及开始时间，`study_manual_steps` 保存分步回答和时间，`study_observations` 保存观察者记录；原任务、邀请、问卷不删除、不重编号。问卷主体仍在 `usability_tests.questionnaire` 中，提交审计保存在 `events`。

模型确认、原文依据、版本指纹、真实求解及独立数值检查仍走原接口。参与者只能读写自己的测试；观察者记录和全量汇总仅管理员可见。删除专用测试会同时删除对应分步记录、问卷和观察记录，且失效关联邀请。
