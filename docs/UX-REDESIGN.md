# OptiFlow V2 用户体验重构

## 代码审查与问题定位

重构前，我先梳理了已有实现：前端为 Streamlit，使用 Session State 导航、SQLite 任务快照及后台 Python 子进程。实时建模通过 AgentAdapter 复用需求解析、技能路由和建模接口；内置案例读取标注模型并真实求解。生成代码用于审阅，实际执行的是已确认模型的受控解释器。

| 用户反馈 | 具体节点 | 重构措施 |
| --- | --- | --- |
| 小字难读 | app.py 的 eyebrow/source/stage-note 使用 11–13px，caption 大量浅灰 | 正文 16px、辅助 14px、标题 28px，统一中性底色与对比度 |
| 反馈和计算冲突 | manual_ui.step_record 强制逐步回答并推进测试步骤，app.model_review 的确认按钮独立调用 confirm_task | 产品四阶段成为唯一主流程；体验反馈独立，业务确认在服务层保存当前版本与指纹 |
| 找不到开始 | 参与者入口、工作台总览、新建任务、顶部测试说明同时提供多组按钮 | 独立导引页，一个“开始体验”主操作；示例为次操作 |
| 同屏内容过多 | app.model_review 的左模型 / 右原文、反馈和求解操作，以及底部测试表单叠加 | 单一工作区，先业务理解，再模型检查；专业信息按需展开 |
| 不清楚下一步 | 页面 page、业务 status、模型版本与 T1–T6 分别推进 | 统一四阶段投影，服务层阻止未确认的求解；修改后所有确认与当前结果失效 |

旧后端已有模型确认、版本检查、求解前指纹校验，能够防止未确认模型直接计算。用户反馈中的“跳步”主要是测试问卷状态与业务状态不一致，不能通过增加问卷门槛解决。V2 需要明确记录业务理解确认，再进行模型确认；辅助入口使用同一服务接口。

## 新信息架构

导引页 → 产品工作台（描述需求 → 确认业务理解 → 检查模型 → 求解与方案）→ 可选的独立体验反馈页。

工作台允许返回已生成内容，浏览未来步骤时说明缺少的条件；只有当前版本的业务规则确认和模型确认完整时才能开始求解。修改业务需求会保存版本历史，清空当前模型、结果及确认，后续展示“待重新生成 / 计算”，不会把旧结果当成当前有效方案。

专业功能保留：模型原文对照、数学表达、JSON、生成代码审阅、真实阶段事件、求解状态、数值检查、版本对比、报告导出、任务记录、Badcase、技能库和管理员统一导出。它们从主路径移入明确命名的详情入口。

## 数据与兼容策略

历史问卷、六任务手册数据和旧任务不删除、不改写。新工作台体验反馈使用版本化问卷，复用 SQLite 收集和 CSV 导出；业务修改与体验问题使用不同接口。新体验流程不强制填写 T1–T6 回答，也不需要先求解基准方案才能修改需求。历史六任务协议仍保留其原始记录和观察者功能，不能将旧指标与 V2 流程混算。

## 设计交付范围

Figma 可编辑画面：导引、需求输入、业务理解确认、模型检查与修改、结果、独立反馈、反馈成功，以及生成中、需要修改、失败 / 校验不通过、结果过期状态。统一字体、颜色、间距、主次按钮、步骤导航、表单与消息组件；按 Streamlit 原生能力实现，不新增前端框架。

Figma 文件：https://www.figma.com/design/XwyaSk6o5YOEOAHBaxAXdI

设计和开发验收使用独立案例数据，不计入真实用户效果。

## 已落地的操作路径

1. 产品导引说明用途、四步路径和示例，一个“开始体验”主入口。
2. 工作台选择内置案例或输入真实业务问题。在线受邀体验按邀请案例运行，明确标注预置模型与真实求解；本机保留实时 Agent 和手动技能选择。
3. 确认规则页先展示通俗目标、实际模型采用的规则与假设。确认无误直接继续，不要求填写意见；需要修改时打开独立业务修改区。
4. 模型检查页说明决策对象、单位、数量域与模型规则。原文对照、公式、JSON 和建模说明折叠展示。明确点击确认后才启动计算。
5. 结果优先展示建议安排、目标值、主要资源用量和限制条件。只有当前模型已确认、求解最优且数值通过时才展示推荐。数量图、残差、代码、版本对比和导出保留在详情中。
6. 任意步骤可以进入独立体验反馈并返回。反馈提交不确认模型、不修改业务、不自动完成体验。结果页“完成体验”仅在当前结果有效且已查看时记录完成。

## 实现文件与状态规则

- `workspace_ui.py`：三大区域、四阶段路径、自然语言 / 数量表单修改、独立反馈与专业详情。
- `theme.py` 与 `.streamlit/config.toml`：16px 正文、14px 辅助、28px 标题、32px 关键数字，224px 可折叠侧栏、48px 按钮、白色卡片与紫色主操作。取消 Streamlit caption 默认透明度以保证对比度。
- `flow.py`：当前阶段与缺失条件投影、事务内业务确认，绑定版本与模型指纹。
- `store.py`、`service.py`：事务认领检查业务确认，求解再次检查业务与模型确认；修改清除当前结果和两项确认，旧模型及结果留在版本记录。
- `hosting.py`、`hosting_ui.py`：新邀请使用 workspace_v2，旧邀请保留 legacy。参与者仍由服务端校验任务归属。
- `usability.py`、`study_ui.py`、`manual_ui.py`：版本化五项问卷、反馈时模型版本、完整事件、后台查看与 UTF-8 CSV 导出。协议、受邀 / 本机 / 历史未标注来源分组统计，避免混算；历史问卷不能被新版接口覆盖。
- `cli.py`：新 CLI 任务也使用 V2；先执行 `--workbench-confirm-business VERSION`，再明确 `--workbench-confirm VERSION`。历史任务保留原协议。

Figma 包含 7 个主要页面、4 个交互状态、239 个可编辑文字节点及 49 条页面连线；按钮、输入等复用 Simple Design System，统一中文字体与本地颜色 / 间距变量。目标技术栈为 Streamlit，未引入 React 或其他 UI 框架。

## 验收记录（2026-10-29）

- `run_experiment.py --workbench-test`：73 项通过，覆盖新旧流程、越级求解阻止、版本失效、权限隔离、问卷独立、不可行结果和历史兼容。
- 最后补充界面控件后的 UI / 模型审阅专项：9 项通过。
- `run_experiment.py --method all --dry_run`：生产、预算、排班三个案例均真实最优求解，目标值分别为 10000、195、2900，数值检查通过；冒烟检查使用 V2 双确认。
- Edge 真实浏览器：1440px 桌面与 390px 窄屏，验证导引、输入、业务确认、模型确认、求解、100 件上限修改及返回反馈；九个截图检查无横向溢出。案例修改前后真实结果可能相同，不伪造方案差异。
- 测试均使用隔离数据库。已有生产数据库通过 SQLite backup 备份，未删除历史任务、参与者回答或问卷。
- 新版外网服务已更新。公网浏览器确认新版参与者导引、管理员登录、V2 体验流程字段与统一导出入口可用；参与者看不到全量导出。上线检查未创建业务任务或提交问卷，旧任务快照和问卷与备份逐项一致。

上述工程验收使用内置案例和已有适配器契约测试，没有新增付费 LLM 调用。实时模型服务的可用性与生成质量仍受部署配置影响。该阶段使用的临时外网入口依赖 Windows 电脑和隧道，当前公开演示已改为 [固定云端入口](RESUME-DEPLOY.md)。

## 后续体验反馈（2026-10-30 更新）

Demo 上线后，我邀请了 15 位用户体验。自动建模与调整功能好评率约 90%，业务范围相关差评率 40%。我会优先扩展案例覆盖和可调整规则，再继续验证首次使用流程。这是本轮功能评价汇总，90% 为约数，没有用来推算改版前后的满意度提升或任务完成率变化。
