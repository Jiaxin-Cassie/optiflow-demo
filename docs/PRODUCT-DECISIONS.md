# 产品决策与迭代

## 1. 为什么把自动建模改成用户决策流程

最初的系统侧重自动生成模型和代码。我在做产品版本时，把重点放在业务人员能否检查目标与限制、发现遗漏并修改要求。原有 Agent 通过适配层复用，我主要补充了确认节点、版本记录和业务解释。

我优先考虑不了解优化的业务人员：首屏先说明用途与开始入口，模型页面先展示业务含义，公式和代码放在详情中。

## 2. 为什么需要业务理解和模型两次确认

业务确认回答“系统是否理解了我的目标和限制”；模型确认回答“决策对象、单位、边界和假设是否代表当前业务”。两者关联同一版本和指纹。

确认记录落在服务端。前端导航只能改变查看位置，不能替代服务端确认。模型发生变化时，原来的确认不能继续授权求解。

## 3. 为什么不强制填写逐步反馈

用户反馈中有一个具体问题：在一个区域被要求填表，在另一个区域却能继续计算。我将业务流程与体验问卷分开；理解正确时直接确认，需要修改时才输入业务要求。

体验问卷使用独立接口，记录易用程度、下一步清晰度、困难环节、操作问题和建议。问卷提交不修改模型，也不自动把业务任务标记为完成。

## 4. 为什么修改后不继续展示旧推荐

模型、人工确认和求解结果之间存在依赖。补充要求后先保存历史版本，再清空当前确认和结果，重新建模。界面说明变更及后续动作，旧结果只能作为历史查看。

新增约束可能不改变最优方案。例如 A≤100 时原方案仍可行，数量和利润可以保持不变；A≤80 时才会改变组合。这两种情况都应按实际计算解释，不为了演示反馈而制造差异。

## 5. 为什么将验证状态分开

求解器的 Optimal 表示对当前模型的求解状态；数值通过表示独立重算满足模型约束；人工复核表示用户确认了业务含义。三者不能合并成“答案正确”。即使全部完成，业务语义仍未经过独立验证。

## 6. 为什么公开 Demo 与正式测试分开

我希望通过简历进入的访客可以直接体验，因此公开版本免邀请码，每个访客使用独立会话。它复用相同工作台、任务服务和求解器，限定内置案例，访客不需要配置模型密钥。

公开演示、受邀测试、本机体验与历史协议分别标注，不能将演示操作计入正式研究效果。长期反馈存储需要可靠的持久化部署，免费云容器的本地 SQLite 不承担这项保证。

## 上线反馈与下一轮迭代

Demo 上线后，我邀请了 15 位用户体验。体验反馈汇总中，自动建模与调整功能的好评率约为 90%，业务范围相关的差评率为 40%。这是小样本的功能评价，90% 保留约数，不代表建模准确率，也没有前后对照的效果结论。

这轮反馈让我把下一轮重点放在业务场景覆盖。我会先整理用户希望解决的具体问题，再补充对应案例和可调整规则，明确每类场景适用的条件。测试时继续观察首次使用者能否找到开始入口、核对规则、完成修改，并读懂最终方案。
